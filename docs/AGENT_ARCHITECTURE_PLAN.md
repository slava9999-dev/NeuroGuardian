## 📋 Шаг 2: "ДАННЫЕ МЕНЯЮТСЯ ЧАСТО?"

Согласно курсу, это ключевой вопрос для выбора подхода:

```
┌─────────────────────────────────────────────────────────────┐
│ ДАННЫЕ МЕНЯЮТСЯ ЧАСТО?                                       │
│                                                               │
│    ДА ─────────────> RAG + In-Context Learning               │
│    │                                                          │
│    │   Много? ──> RAG (retrieval из базы знаний)             │
│    │   Мало?  ──> In-Context Learning (в промпт)             │
│    │                                                          │
│    НЕТ ────────────> Fine-tuning (если специфичный домен)    │
│                      Prompting (если общие знания)            │
└─────────────────────────────────────────────────────────────┘
```

### Применяем к NeuroGUARDIAN:

| Тип данных                | Меняется часто?        | Много данных? | Рекомендация                        |
| ------------------------- | ---------------------- | ------------- | ----------------------------------- |
| **Цены товаров**          | ✅ Постоянно           | Много (сотни) | **RAG** → БД запросы                |
| **Комиссии WB/Ozon**      | ❌ Редко (раз в месяц) | Мало          | **Prompting** → в системном промпте |
| **Правила маркетплейсов** | ❌ Редко               | Среднее       | **RAG** (docs) или Prompting        |
| **Продажи пользователя**  | ✅ Каждый день         | Много         | **RAG** → БД запросы                |
| **Статус защиты**         | ✅ Динамично           | Мало          | **State Management**                |
| **Контекст диалога**      | ✅ Каждое сообщение    | Мало          | **In-Context Learning**             |
| **Персональность Viktor** | ❌ Никогда             | Мало          | **Prompting**                       |

## 🔧 Шаг 3: ТЕКУЩАЯ АРХИТЕКТУРА vs ИДЕАЛЬНАЯ

### Текущая архитектура (v4):

```
┌──────────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR V4                            │
│                                                               │
│  ┌─────────┐    ┌───────────┐    ┌───────────┐               │

│  └─────────┘    └───────────┘    └───────────┘               │

│       v                                                       │
│  [Статический промпт system-v5.ts]                           │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

**Проблемы:**

1. ❌ Промпт статический (570 строк!) — медленно, дорого
2. ❌ Нет RAG — знания о комиссиях захардкожены в промпте
3. ❌ Слабый State Management — нет памяти между сессиями
4. ❌ Нет валидации вывода — LLM может галлюцинировать
5. ❌ Нет Memory Management — история диалога обрезается

### Идеальная архитектура (v5 — по курсу):

## 🎯 Шаг 4: ЧТО КОНКРЕТНО НУЖНО УЛУЧШИТЬ

### Приоритет 1: CRITICAL (влияет на точность и надёжность)

#### 1.1 Dynamic Prompt Assembly ✅→ НУЖНО

**Зачем:** Промпт 570 строк = дорого + медленно + шум для модели

**Решение:**

```typescript
// Вместо одного большого промпта
const systemPrompt =
  STATIC_CORE + // 50 строк: личность + правила
  getRelevantKnowledge(query) + // RAG: только нужные факты
  getUserState(userId) + // State: контекст пользователя
  getRecentHistory(userId); // Memory: последние 5 сообщений
```

**Эффект:** -70% токенов, +30% точность (меньше шума)

#### 1.2 State Management ✅→ НУЖНО

**Зачем:** Виктор "забывает" контекст между сессиями

**Что хранить:**

```typescript
interface UserState {
  // Статическое (редко меняется)
  marketplace: 'WB' | 'Ozon' | 'both';
  hasApiKeys: boolean;
  productsCount: number;

  // Динамическое (каждую сессию)
  lastQuery: string;
  pendingAction?: { type: string; params: object };
  awaitingResponse?: 'cost_price' | 'period' | 'confirmation';

  // Метаданные
  lastActiveAt: Date;
  totalQueries: number;
}
```

#### 1.3 Memory Management ⚠️→ ЧАСТИЧНО ЕСТЬ

**Текущее:** История обрезается до 5 сообщений в промпте

**Улучшение:**

- Важные факты → Long-term memory (DB)
- Текущая сессия → Short-term (in-context)
- Примеры решений → Few-shot примеры

## 📐 Шаг 5: ПЛАН РЕАЛИЗАЦИИ

### Фаза 1: State Management (2-3 часа)

1. Создать `StateManager` класс
2. Сохранять состояние в PostgreSQL (user_state таблица)
3. Интегрировать в orchestrator

### Фаза 2: Dynamic Prompt (2-3 часа)

1. Разделить промпт на модули:
   - `core.ts` — личность (неизменное)
   - `tools.ts` — описания инструментов
   - `knowledge.ts` — динамические знания
2. Создать `PromptBuilder` класс
3. Собирать промпт динамически

### Фаза 3: RAG Integration (3-4 часа)

1. Активировать AgentKnowledgeBase
2. Добавить retrieval в PromptBuilder
3. Загрузить документы с комиссиями

### Фаза 4: Validation Layer (2 часа)

1. Расширить validateAnswerLinks
2. Добавить проверку чисел
3. Добавить проверку названий товаров
