# Анализ архитектуры RAG: PgVector vs Google Ready-Made

**Дата:** 15.01.2026
**Статус:** Решение принято (Оставить PgVector)

## 1. Контекст

От пользователя поступил запрос на анализ возможности использования готовых RAG-инструментов от Google (File Search API / Vertex AI) вместо текущей самописной реализации на Postgres + pgvector.

## 2. Сравнение решений

### А. Текущее решение (Custom RAG on PgVector)

**Архитектура:**

- **Store:** Neon Tech Postgres (бесплатно)
- **Engine:** pgvector extension (векторный поиск)
- **Embeddings:** Gemini text-embedding-004 (через Google API)
- **Logic:** TypeScript (VectorStore.ts)

**Плюсы:**

1. **Полный контроль:** Мы владеем данными и алгоритмами поиска.
2. **Vendor-agnostic:** Легко сменить провайдера эмбеддингов (OpenAI, Cohere, Llama).
3. **Скорость:** Локальный поиск в БД (RunTime < 500ms).
4. **Цена:** Полностью укладывается в Free Tier (Infrastructure-less).

**Минусы:**

1. Требует поддержки кода ингестии (`setup-vector-store.ts`).
2. Примитивный алгоритм чанкинга (по заголовкам Markdown).

---

### Б. Google File Search API (Новинка 2024/25)

**Архитектура:**

- Файлы загружаются в Google Cloud.
- Google управляет индексацией и поиском (Black box).

**Плюсы:**

1. **Zero Ops:** Не нужна база данных, не нужен скрипт нарезки.
2. **Качество:** Google использует продвинутые алгоритмы семантического чанкинга.
3. **Интеграция:** Работает нативно с Gemini моделями.

**Минусы:**

1. **Vendor Lock-in:** Жесткая привязка к экосистеме Google.
2. **Latency:** Дополнительные сетевые задержки при "обдумывании" файлов.
3. **Приватность:** Данные физически покидают наш контур хранения.
4. **Гибкость:** Нельзя легко добавить фильтрацию по нашим метаданным (user_id, subscription_tier), так как файлы "общие" в контексте сессии или корпуса.

## 3. Рекомендация

**Оставить текущее решение (Option A).**

Причины:

1. **Prod-Ready:** Система уже внедрена, оттестирована и работает стабильно.
2. **Скорость:** Для чат-бота критична низкая задержка. SQL-запрос быстрее API-вызова к Google Knowledge Store.
3. **Специфика:** У нас маленькая база знаний (~100 КБ). Использование тяжелых Enterprise-инструментов Google избыточно.

## 4. План улучшений (Roadmap)

Вместо смены движка, предлагаются следующие оптимизации текущего стека:

1. **Long Context Fallback:**
   Для сложных запросов (например, "проанализируй всё") отправлять в LLM весь контент базы знаний (благо окно Gemini 1M токенов позволяет), минуя векторный поиск. Это даст 100% точность для аналитических задач.

2. **Hybrid Search:**
   Внедрить поиск по ключевым словам (Postgres Full Text Search) параллельно с векторным, чтобы находить точные совпадения (артикулы, термины).

3. **Re-ranking:**
   (Если качество поиска упадет) Добавить шаг переранжирования результатов с помощью Cross-Encoder модели.
